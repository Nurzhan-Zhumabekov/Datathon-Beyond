# BEYOND — контроль кассовой дисциплины по видео (Datathon 26 · ForteBank)

Сервис принимает видеозапись работы кассира (.mov), находит визуально наблюдаемые признаки возможных нарушений
кассовой дисциплины и возвращает вердикт, таймкод, кадры‑доказательства с разметкой, вероятность, описание и
нормативное основание. Анализ выполняет **каскад из двух локальных моделей**: быстрый сканер Qwen3‑VL‑4B и
эксперт Qwen3‑VL‑8B, к которому эскалируются только подозрительные моменты.
**Все модели работают локально** (Apple Silicon, MLX): при обработке видео сервис не обращается к облачным
AI‑сервисам и не требует интернета после загрузки весов.

- Веб‑интерфейс (дашборд): `https://<адрес>/`
- API: `POST https://<адрес>/api/v1/analyze`, `GET https://<адрес>/api/v1/jobs/{job_id}` (заголовок `X-API-Key`)

---

## 1. Запуск

Требования: Mac на Apple Silicon (M1–M4), 16 ГБ RAM, macOS 14+, Homebrew, ~10 ГБ на диске.

```bash
brew install ffmpeg uv cloudflared
uv venv --python 3.12 .venv
uv pip install --python .venv fastapi "uvicorn[standard]" python-multipart av pillow numpy pyyaml httpx mlx-vlm
./scripts/download_models.sh      # Qwen3-VL-4B (3,1 ГБ) и Qwen3-VL-8B (5,8 ГБ) в ./models — один раз
./start.sh
```

`start.sh` поднимает сервис на `127.0.0.1:8000`, не даёт Mac уснуть (`caffeinate`) и открывает публичный HTTPS‑адрес:
через ngrok (постоянный бесплатный домен аккаунта — адрес не меняется после перезапуска) или, если ngrok не настроен,
через Cloudflare Quick Tunnel. Адрес печатается в консоли и сохраняется в `data/public_url.txt`. API‑ключ создаётся автоматически при
первом запуске и хранится в `.env` (в репозиторий не попадает).

Если весов эксперта (8B) нет, сервис работает только со сканером (4B) — каскад включается автоматически, когда веса
загружены.

Проверка «как у жюри» (загрузка видео через API, проверка схемы ответа, подсчёт метрик):

```bash
.venv/bin/python scripts/jury_sim.py --base http://127.0.0.1:8000 \
  --videos ~/Downloads/open/videos --labels ~/Downloads/open/open_labels.xlsx
```

### Переменные окружения (необязательно)

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `MAX_UPLOAD_MB` | 200 | максимальный размер загружаемого видео (больше — ответ 413) |
| `TIME_BUDGET_SEC` | 200 | бюджет анализа одного видео при пустой очереди |
| `UI_BUDGET_SEC` | 120 | бюджет анализа видео, загруженного через сайт (задания API жюри идут первыми) |
| `SKIP_UNCHANGED` / `CHANGE_THRESHOLD` | 1 / 5.0 | не перечитывать неизменившийся кадр |
| `VLM_MODEL` / `JUDGE_MODEL` | `./models/…4B…`, `./models/…8B…` | пути к моделям сканера и эксперта |

С сайта в очереди может ждать не больше одного видео (иначе 429). Тесты: `.venv/bin/python -m pytest -q tests`.

## 2. Использование

**Дашборд.** Перетащить видео (или выбрать файл / вставить ⌘V) → на экране «Ход анализа» видно, какой этап идёт:
сканер 4B, правила, эскалация в 8B, отчёт. Результат:
- вердикт «Нарушение не обнаружено» / «Обнаружены признаки возможных нарушений» и цепочка анализа
  (сколько кадров просканировано, сколько подозрений эскалировано и отклонено экспертом);
- KPI: число нарушений, максимальная вероятность, число эскалаций в 8B, длительность видео и время анализа;
- видеоплеер с **красной рамкой поверх видео** в момент нарушения;
- карточки нарушений: тип, таймкод, уверенность модели (высокая/средняя/низкая), отметка «подтверждено экспертом 8B»,
  что видно на видео, почему это может быть нарушением, кадры‑доказательства с рамкой, норма со ссылкой на adilet;
- хронология: видео, разбитое на участки (кассир один / с посетителем / 3+ человека / кассира нет) с метками нарушений;
- «Последние проверки» и открытие результата по ссылке `/?job=<id>`.

**API.**

```bash
curl -X POST https://<адрес>/api/v1/analyze -H "X-API-Key: <ключ>" -F "file=@video_017.mov"
# {"job_id":"3f2a9c1e0b11","status":"processing"}
curl https://<адрес>/api/v1/jobs/3f2a9c1e0b11 -H "X-API-Key: <ключ>"
```

Статусы: `processing` (в т.ч. ожидание в очереди), `done`, `failed`. Ответ `done` строго по схеме ТЗ:
`verdict` (`violation` / `no_violation`), `violations[]` с полями `type`, `timecode_sec`, `description`,
`evidence_frames[]` (1–3 JPEG в base64, кадр с рамкой вокруг ключевого объекта). В `description` — что видно,
вероятность и нормативное основание. Без верного ключа — `401`, неизвестный `job_id` — `404`.
Видео, загруженные через API, удаляются сразу после обработки.

## 3. Архитектура: каскад из двух моделей

```
 .mov ─► FastAPI (/api/v1 с ключом, /ui) ─► очередь заданий (JSON‑файлы, 1 воркер, бюджет времени) ─► конвейер
   1. Декодирование (PyAV): кадры 2 к/с с реальными временными метками (PTS), учёт поворота
   2. СКАНЕР · Qwen3‑VL‑4B: кадр раз в 1,5 с (не более 30 кадров на видео: для 145‑секундного ролика шаг ≈ 4,8 с;
      если сканер работает медленнее плана, оставшиеся кадры равномерно прореживаются, чтобы покрыть всё видео) →
      {людей в помещении, кассир на месте, телефон, личные вещи, еда/напиток}; неразобранный ответ модели
      переспрашивается, иначе берётся состояние предыдущего кадра; неизменившийся кадр не перечитывается
   3. ПРАВИЛА по таймлайну:
        • уход кассира → «что осталось»: стол крупным планом (эксперт 8B перечисляет предметы) и экран ноутбука ×4
          (открытая программа или экран блокировки)
        • вход посетителя → лежат ли наличные на столе; короткий визит (инкассатор ушёл сразу)
        • телефон / личные вещи / еда, пока кассир один; 3+ человека в помещении
   4. ЭСКАЛАЦИЯ · Qwen3‑VL‑8B: каждое подозрение перепроверяется на 3 кадрах вокруг момента →
        подтверждено / отклонено, вероятность 0–100, фактическое описание, рамка вокруг ключевого объекта.
        Если правила ничего не нашли — эксперт просматривает видео окнами по ~6 с («второй взгляд»).
   5. ОТЧЁТ: тип из реестра rules.yaml, таймкод, 1–3 кадра с рамкой, описание без оценочных суждений, норма
```

| Компонент | Что используется | Лицензия |
|---|---|---|
| Сканер | **Qwen3‑VL‑4B‑Instruct** (4‑bit, MLX) | Apache‑2.0 |
| Эксперт (эскалация) | **Qwen3‑VL‑8B‑Instruct** (4‑bit, MLX) | Apache‑2.0 |
| Инференс на Apple Silicon | `mlx`, `mlx-vlm` | MIT |
| Видео | PyAV / FFmpeg | BSD / LGPL |
| Сервер | FastAPI, Uvicorn | MIT / BSD |
| Публичный адрес | Cloudflare Tunnel (`cloudflared`) — только транспорт, без AI | Apache‑2.0 |

Почему так:
- **Каскад вместо одной большой модели.** 4B быстро читает все кадры, 8B тратит время только на спорные моменты:
  отсекает ложные срабатывания и даёт более точное описание и рамку.
- **VLM вместо обученного детектора.** Датасет — 40 роликов без разметки типов, финальное видео снято под другим
  углом, в обучающих данных уже несколько ракурсов. Модель «понимает» сцену с любого ракурса, правила не завязаны
  на координаты в кадре.
- **Модель не придумывает выводы и ссылки.** Модели отвечают на узкие вопросы о кадрах. Вывод о нарушении делают
  явные правила, тип и норма берутся из реестра `app/pipeline/rules.yaml`; оценочные фразы из описаний модели
  отфильтровываются.
- **5 минут даже при очереди.** Лимит жюри считается от загрузки. Задания API (жюри, с ключом) всегда идут в очереди
  раньше загрузок с сайта; с сайта в очереди может ждать не больше одного видео, лимит файла 200 МБ, анализ с сайта —
  не дольше 120 с. Воркер делит оставшееся время между текущим видео и ожидающими (до 200 с, если очередь пуста);
  каждая дорогая проверка (осмотр стола ≈25 с, эксперт 8B ≈25 с) запускается, только если на неё хватает бюджета.
- **Расширяемость.** Новое правило = блок в `rules.yaml` + условие в `detect_events`; модели задаются через
  `VLM_MODEL` / `JUDGE_MODEL`.

## 4. Нормативная база и принцип сопоставления

| Документ | Где |
|---|---|
| Правила осуществления кассовых операций и операций по инкассации банкнот, монет и ценностей в БВУ … — постановление Правления НБРК от 29.11.2019 № 231 | https://adilet.zan.kz/rus/docs/V1900019680 |
| Правила организации охраны и устройства помещений БВУ … — постановление Правления НБРК от 24.02.2020 № 14 | https://adilet.zan.kz/rus/docs/V2000020075 |
| Требования к обеспечению информационной безопасности банков … — постановление Правления НБРК от 27.03.2018 № 48 (по справочным системам утратило силу 03.04.2026; актуальный акт АРРФР уточняется) | https://adilet.zan.kz/rus/docs/V1800016772 |

Принцип: для каждого типа нарушения в реестре записаны (1) что именно должно быть видно на видео, (2) пункт нормы,
(3) формулировка без неподтверждённых предположений. Сервис не делает выводов о том, чего не видно на видео
(проводки, сверка, подлинность купюр, намерения людей). Результат — подсказка для проверяющего, а не заключение.

## 5. Распознаваемые типы нарушений

| Тип | Что видно на видео | Основание |
|---|---|---|
| Оставление ценностей на рабочем месте без присмотра | Кассир уходит, на столе остаются деньги/пачки/сумка/планшет/посторонние предметы | Правила № 231, п. 20 |
| Оставление рабочего компьютера без блокировки | Кассир уходит, на экране ноутбука открыта рабочая программа (не экран блокировки) | Требования ИБ, п. 71 пп. 9 (см. примечание выше) |
| Оставление рабочего места во время обслуживания клиента | Кассир уходит, когда в помещении находится посетитель | Правила № 231, п. 22 |
| Использование мобильного телефона на рабочем месте | Телефон в руках кассира, когда кассир один | Правила № 231, п. 12 |
| Личные вещи на рабочем месте кассира | Сумка/верхняя одежда на столе; кассир ест или пьёт во время работы с ценностями | Правила № 231, п. 12 |
| Присутствие постороннего лица в кассовом помещении | Дополнительное лицо помимо кассира и обслуживаемого клиента | Правила № 231, п. 75; Правила № 14 |
| Нарушение порядка приёма ценностей от инкассатора | Посетитель передаёт сумку/ценности и уходит через несколько секунд — проверки целостности и пломбы в его присутствии не видно | Правила № 231, пп. 24–25 |
| Наличные открыто лежат на столе при входе посетителя | В момент входа другого лица на столе лежат наличные вне хранилища | Правила № 231, п. 20 |
| Нарушение порядка приёма/выдачи наличных | Наличные передаются без видимого пересчёта в присутствии клиента (находит эксперт 8B) | Правила № 231, п. 20, п. 31 пп. 4 |
| Иное возможное нарушение | Эксперт 8B на «втором взгляде» видит и подтверждает нарушение, которого нет в реестре | Источник не определён — требуется проверка человеком (ссылка не выдумывается) |

Таймкод для нарушений «по бездействию» (ушла, не убрав/не заблокировав): момент начала ухода кассира (~3,5 с до того,
как она пропадает из кадра) — именно тогда ещё можно было выполнить обязательное действие.

## 6. Измеренное качество (40 уникальных видео обучающего набора)

Прогон через API тем же способом, что и у жюри (`scripts/jury_sim.py`), версия от 17.10 19:00:

| Метрика | Значение |
|---|---|
| Верный вердикт по видео | 24 из 40 (60%) |
| Найдено нарушений | 13 из 21 видео с нарушением |
| Ложные срабатывания | 8 из 19 чистых видео |
| Ошибка таймкода (медиана) | 2,5 с |
| Максимальное время на видео | 227 с (лимит 300 с) |

Основные источники ложных срабатываний (исправлены после замера): «второй взгляд» эксперта принимал обычный уход
кассира за нарушение; модель называла счётную машину и денежный ящик «устройством»/«кассовым аппаратом».
Число «уверенность модели» — не откалиброванная вероятность, а оценка модели; используется для сортировки.

## 7. Ограничения и известные ошибки

- Разрешение видео низкое (464×848): мелкие предметы (телефон в руке, одна купюра) видны ненадёжно.
- Нарушения во время обслуживания клиента (передача денег, пересчёт) распознаются хуже всего; «второй взгляд»
  эксперта иногда принимает обычного клиента за постороннего.
- Подсчёт людей может ошибаться из‑за отражений в стеклянной стене.
- Скорость на MacBook Air M4: ~1,5–2,5 мин на видео 15–25 с (сканер + эскалации). При очереди число кадров
  автоматически уменьшается, чтобы уложиться в 5 минут, что снижает точность.
- Сервис работает, пока Mac включён, не спит и подключён к сети. Бесплатный ngrok показывает браузеру страницу‑предупреждение
  перед первым открытием сайта (кнопка «Visit Site»); на запросы к API это не влияет.
